# Repository Audit and Parallel-Work Handoff

This audit reflects the repository posture observed on July 10, 2026. It is a working coordination document, not a replacement for live GitHub checks, `STATUS.md`, `EVIDENCE.md`, or release receipts.

## Parallel-work lanes

Use one owner per lane and avoid multiple chats editing the same files.

### Lane A — Release engineering

Owns:

- Canonical workflow consolidation.
- Exact-head CI.
- Deployment receipt.
- Rollback.
- Custom-domain smoke.
- Status truth.

Must not change:

- Founder pitch or investor wording without claims review.

### Lane B — Product and spatial experience

Owns:

- Home-to-Replay journey.
- Final assets.
- Motion, sound, loading, fallback, accessibility, and mobile quality.
- Visual acceptance evidence.

Must not claim:

- Provider or device certification from source presence.

### Lane C — Identity, memory, and privacy

Owns:

- Authentication.
- Tenant isolation.
- Memory ownership.
- Passport permissions.
- Export, deletion, revocation, retention, and audit.

Must not enable:

- Real-user sensitive memory until ownership and data-rights tests pass.

Owns:

- Demo scripts.
- Website and event copy.
- Claims matrix.
- Beta cohort materials.

Owns:

- Entity registry.
- Chain of title.
- Assignments and licenses.
- Securities and fundraising review.
- Privacy and health-adjacent legal review.

Must not:

- Rewrite historical executed documents to make them appear current.

## Merge-order rules

1. Never merge a stale branch because its description sounds complete.
2. Rebase or recreate focused changes on current `main` when the branch has drifted materially.
3. Prefer small, single-purpose PRs.
4. Do not mix deployment-control, visual-asset, user-data, marketing-copy, and legal-document changes in one PR.
5. Require exact-head checks for the change being reviewed.
6. A merged PR is not a deployed capability.
7. A deployed route is not a certified provider or device capability.
8. A document or file name containing a version is not proof that the version is complete.
9. Preserve receipts and record the exact SHA they prove.
10. Update public claims only after evidence changes.

## Weekly founder review

Review these ten questions:

1. What exact SHA is deployed?
2. What exact SHA is the rollback target?
3. Which routes are proven on the public domain?
4. Which enabled features use real user data?
5. Is every enabled record user- and tenant-scoped?
6. Which assets are selected production assets versus fallbacks?
7. What did beta users repeatedly do without coaching?
8. What claim became newly supportable this week?
9. What claim must be removed or qualified?
10. What single milestone most reduces investment or launch risk next?
