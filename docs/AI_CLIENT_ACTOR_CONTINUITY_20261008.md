# Council and Orb client actor continuity

The existing Council JSON adapter and OpenAI streaming adapter captured a Firebase user before awaiting credentials, then sent or returned a result without verifying that the same SDK actor still owned the request. Isolated actual-source fixtures reproduced stale dispatches after a user replacement or logout and stale answers after response headers or bytes arrived. These are local source defects; the fixtures did not establish deployed leakage.

Both adapters now use one small client boundary that captures the actual SDK user object and UID. It checks that identity before dispatch and after each awaited phase, subscribes to SDK ID-token notifications, and owns a private cancellation signal. A same-object token refresh remains valid. A replacement SDK user with the same UID, logout, a different user, an observer error, or caller cancellation closes the request. Pending credentials, headers and body reads cannot delay the caller's cancellation merely by ignoring the signal. Late promise rejections are consumed; unread late responses receive best-effort, non-blocking cancellation.

The OpenAI adapter also checks the actor before and after each streaming callback and at EOF. Both adapters preserve the existing endpoints, raw outgoing message and bounded context, intent IDs, language validation, consent requirements, provider failure classifications and disclosed fallbacks. No retry, provider authority, consent grant, paid-operation bypass or server policy change is introduced.

The existing Council and Orb panels use a stable SDK-derived external-store snapshot with an unavailable server snapshot. A changed actor generation remounts the internal panel with fresh prompt, history, result, processing consent and voice-consent state. Their asynchronous continuations independently check the captured snapshot before publishing an answer, stream fragment, error fallback or voice action. Actor watchers and unmount cleanup abort the active request; Orb also stops its existing voice playback and removes its external voice permission. Guest deterministic fallback behavior remains available under the existing consent flow.

## Validation scope

- 45 actual transpiled client/helper tests pass with synthetic SDK identity events and HTTP terminals. The identical suite against the unchanged two client implementations produces 21 passes and 24 failures, with no skips or cancellations.
- The eight retained provider-registry tests pass after giving the existing synthetic user its required UID and asserting the new private-signal lifecycle. They retain provider readiness, denial, error classification and actual React server-rendered Council/Scenario assertions.
- Strict selected type checking covers all five runtime files and their exact copied dependency closure with the declared Firebase, React and Next interfaces. Local tools are Node 24.19.0 and TypeScript 6.0.3; native Node 22 proof is separate.
- The new workflow checks an exact clean commit, installs frozen dependencies, runs project and strict selected type checks, executes both scoped suites and records source hashes. A queued run is not a passing receipt.

SDK notifications and React scheduling govern when already-rendered panel state is reset. Direct actor checks also guard asynchronous request and panel continuations; this document does not claim instantaneous screen clearing, mounted-browser acceptance or actual account-transition behavior on a device. Cancellation cannot retract data already admitted by a remote provider. Native fetch and SDK credential acquisition may continue internally after the local caller has closed; this boundary prevents a late continuation from creating a new dispatch or publishing a stale result. Remote enforcement, deployed parity, provider canaries, hardware behavior, whole privacy acceptance and release certification remain separate gates.

The source adds no new ownership claim, account mutation, legal consent certification, real credential, provider call, payment, cloud write, export or deletion operation. User export and deletion rights and server-side consent authority are unchanged.
